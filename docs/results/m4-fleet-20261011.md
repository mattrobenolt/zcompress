# M4 fleet run: the zstd decoder against the pinned competitors (+ the snappy gap closed)

Run: `bench-results/20261011T014512Z-m4` (local, gitignored; the run id and
this file are the durable record). Manifest: 7/7 targets, 6 arms, 750 rows
per target, `rounds=5`, `evidence=sufficient`, `errors: none`. The expected
tool-scope warnings per target: the flate-family arms carry no snappy/zstd
rows, googlesnappy no flate-family/zstd, zstd-c no flate-family/snappy.

- Targets: c7i, c8i, c7a, c8a, c7g, c8g, c9g.
- Arms: `zc` (zcompress), `klauspost` v1.18.1-pinned (`zstd.DecodeAll`,
  one-decoder-concurrency), `zstd-c` v1.5.7 (the NEW arm: the pinned
  tarball via `bench/build.zig.zon` + zig fetch, cmake/zig-cc, the driver
  runs whole-buffer `ZSTD_decompressDCtx` with `windowLogMax` 27), the
  in-binary `std.compress.zstd` rows riding the zc arm, plus the flate
  family's arms re-run (libdeflate, zlib-ng, googlesnappy).
- Corpus: the ten `.zst` blobs — the pinned zstd CLI v1.5.7 at level 1 (the
  harness-wide fast-class convention) over the same raw shapes, every blob
  gated on `zstd.decode.decompress` reproducing the raw bytes exactly before
  writing (the inverse of the M3 pattern: no encoder until M5, so the CLI
  produces and our decoder verifies). Frames carry XXH64 checksums, so the
  checksum path is exercised.
- Protocol: the M3 run's — seeded balanced Latin-square rounds, last-core
  isolation, per-round corpus-hash verification, exact intervals, outliers
  reported never removed, A/A noise floors.

### The zstd decoder story

zcompress beats the C reference on the ARM and AMD targets — 0.51-0.84
(c7g/c8g/c9g/c7a/c8a: up to 2x faster than zstd v1.5.7) — and trails it on
the Intel targets (c7i 1.16, c8i 1.30): the first-pass decoder beats the
tuned C set on five of seven, with the Xeon gap as the measured perf
target. klauspost's zstd decoder is behind nearly everywhere (0.25-0.32 on
the ARM/AMD targets, ~0.89 on Intel); std's in-tree decoder is behind
everywhere (0.32-0.78). A/A floors 0.9998-1.0006.

### The snappy competitor-set gap, closed

The M3 run's recorded gap (google/snappy C++ — the plan's pinned snappy
competitor — was not wired) closes here: google/snappy 1.3.1 rode the same
run. snappy compress: zcompress is 4-6x faster than the canonical C++
(0.17-0.23). snappy decompress: competitive, 1.15-1.23 (the canonical
decoder leads by ~15-23%; the M3 klauspost rows, 0.74-0.92, still stand
from that run's data — both competitors now measured).

### The flate family, re-run

The flate/gzip/zlib rows re-ran with the same arms and agree with the M3
run within the noise floors (the full tables are in the run's report.md;
the M3 results file remains the flate-family record, the M4 re-run its
replication).

## What this run decides

- The Intel zstd-c gap (1.16-1.30) is the decoder's measured perf target —
  the entropy-kernel measure-then-optimize notes (readExtra's chunked
  11-bit reads, the raw-block staging copy, huff0's peek loop) are the
  candidates; a perf wave owns it after M4 closes.
- snappy decode's 1.15-1.23 vs the canonical: a smaller gap, same wave.
- No regression action for zstd decode elsewhere: beating the reference
  set on five of seven targets and every in-tree alternative on all seven
  is the M4 acceptance bar met with room.
